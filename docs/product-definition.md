# Harness · Lab 产品定义（v1 草案，2026-09）

> 本文替代 README 中"可视化工作台规范"的定位，作为后续规范、数据契约与参考实现的上位文档。
> 配套文档：[论文方案](paper-proposal.md)。

---

## 一、为什么要重新定义

2026 年 3 月提出本项目时，"harness 是独立的工程对象"还是一个需要论证的主张。半年后的情况是：

1. **主张已成共识。** OpenAI、Martin Fowler、LangChain 等均以 harness engineering 为题发文；LangChain 不换模型、只改 harness，在 Terminal-Bench 2.0 上从 30 名外进入前 5。"把 harness 命名出来"不再构成贡献。
2. **自动 harness 优化成为热点。** Meta-Harness、MemoHarness、HarnessCompass、PRISM、HarnessDev 等相继出现，改 harness 的主体正在从人变成优化器。
3. **随即出现了对这些"提升"是否真实的质疑。** *Rethinking the Evaluation of Harness Evolution* 指出，在匹配预算下，自动演化并不稳定地优于简单的 test-time scaling，留出泛化有限；*Bad Genius* 指出优化器会找到基准级捷径；*Don't Blame the LLM* 发现 35 个连续的 harness 版本在固定模型下没有显著提升，token 却几乎翻倍。
4. **harness 与模型强耦合，并且会过期。** 同一机制在弱模型上是"支架"，在强模型上可能变成"成本"甚至负贡献（*An Empirical Study of Harness Design for Coding Agents*、*More Is Not Always Better*）。
5. **通用观测与评测平台已经覆盖了 trace diff 和实验对比**（Braintrust、LangSmith、Langfuse、Harness.io AgentTrace）。以 UI 为核心，就是在别人的主场竞争。

因此要调整的不是核心判断，而是**产品站在哪个位置**：改 harness 的人和工具越来越多，但判断一次改动是否真的有效，仍然没有可信、便宜、可落地的手段。

## 二、一句话定义

> **Harness Lab 是 agent harness 的变更验证引擎。**
> 对每一次 harness 改动、每一次模型升级、每一份自动优化器提交的候选，它回答三个问题：**真的变好了吗？好在哪个机制？哪些机制现在可以删了？**

它不是 agent 框架，不是观测平台，也不是自动优化器。它是这三者之间的**裁判层**。

## 三、目标用户与使用时刻

**首要用户：** 在生产环境维护 To B agent（合同审核、业务审批、客服、办公流程）的工程团队。典型特征：
- 使用国产模型（GLM、DeepSeek、Qwen 等），模型每 1–3 个月换代一次；
- 私有化部署，SaaS 评测平台难以接入；
- harness 里积累了大量"补丁式"机制（调用修复、重试、策略前置、校验门），没人说得清哪些还在起作用。

**三个使用时刻（产品的核心场景）：**

| 时刻 | 触发 | 用户要的答案 |
|---|---|---|
| **合入前** | 工程师改了一个机制，或新增一个机制 | 这次改动在 pass^k 意义上是否显著变好？有没有让某类任务退化？成本变化多少？ |
| **换模型时** | 基座模型升级或切换 | 旧 harness 里哪些机制已被新模型"吸收"、可以删除？哪些变成了负贡献？ |
| **优化器提交候选时** | Meta-Harness 类工具或内部自动调优产出新 harness | 这份提升能在留出任务上复现吗？是不是捷径？和同预算的重试基线比如何？ |

**次要用户：** 评估外部 agent 厂商的采购与产品决策者（后续扩展，不作为 MVP 目标）。

## 四、核心概念（数据模型）

以下对象构成 M2 数据契约的骨架。所有对象落在 OpenTelemetry GenAI 语义约定之上，只**扩展**属性，不另起一套 trace 格式。

- **Mechanism（机制）**：harness 中一段可独立开关的代码或配置。每个机制必须声明：
  - `id`、`stage`（沿用八段解剖：task / agent / profile / policy / tool_call / artifact / verifier / claim）
  - `kind`：
    - `reactive`（反应式）：只在特定事件发生时介入，例如 schema 修复、循环打断、校验门、声明门；
    - `persistent`（常驻式）：从第 0 步起持续生效，例如策略前置、工具范围收窄、系统提示重建。
  - `trigger`：对反应式机制，给出"本来要介入"的判定点。
- **Config（配置）**：一组机制的开关状态，加上模型、推理强度等参数。任意两份 Config 可以比较。
- **Suite / Task**：任务集，必须标注 `split`（dev / holdout），以及可选的领域标签。
- **Trial**：一个 Config 在一个 Task 上的一次执行，包含完整 trace。
- **Activation（介入事件）**：反应式机制在某一步的触发记录。**包括影子模式下"本来会触发、但未执行"的记录**（见第五节）。
- **Verdict（判定）**：一次比较的结论。包含效应估计、置信区间、pass^k、分任务退化列表、成本差异，以及所用的估计方法和样本量。**判定是一等对象**，可以被 CI 读取，也可以作为 PR 评论输出。

## 五、差异化能力：影子机制（Shadow Mechanisms）

这是 Harness Lab 区别于通用评测平台和已有学术工作的核心，也是配套论文的主题。

**1. 影子模式。** 反应式机制可以在"影子"状态下运行：检测到触发条件时只记录 Activation，不执行干预。影子模式可以在生产流量上常开，成本接近零。

**2. 触发条件分叉估计。** 反应式机制在未触发的轨迹上不改变任何东西，因此它的效应可以分解为：

```
Δ(机制) = P(触发) × E[结果差 | 触发]
```

只需要在影子记录的触发点处分叉：同一前缀，一支执行机制，一支不执行，再加一支同配置对照分叉，用来扣除采样和环境重放噪声。相比整条轨迹重跑的 leave-one-out，这种方法把算力集中在机制真正起作用的地方。

**3. 零成本衰减信号。** 模型升级后，只要对比影子模式下的触发率，就能在不做任何消融的情况下给出"可能已被吸收"的机制清单，再对这份清单做有针对性的分叉验证。

**4. 常驻式机制的处理。** 常驻式机制退化为从第 0 步开始的配对 A/B，同样纳入 pass^k 和置信区间。机制之间的交互效应用小规模析因设计，只在触发点重叠的机制对上做。

> 需要正视的风险：分叉重放要求环境可以重建到分叉点，τ 系列评测里的用户模拟器也是随机的；公共随机数耦合在某些情况下会给出误导性的零效应（见论文方案第四节）。这些都必须在方法里处理，不能忽略。

## 六、产品形态

**开源核心（MVP）：**
1. **机制注册 SDK**：用装饰器或配置声明机制的 `stage / kind / trigger`，自动产生 Activation 事件，并支持影子模式。首个适配目标为 DeepSeek Harness（dsh），机制以 dsh 插件形式实现。
2. **CLI**：
   - `hlab compare A B --suite X --k 8` → Verdict
   - `hlab attribute --config A --mechanisms ...` → 各机制的效应与区间
   - `hlab upgrade-audit --from model_old --to model_new` → 基于影子触发率的删除候选清单，并对候选做分叉验证
3. **报告**：静态 HTML。现有概念稿（机制侧栏、八段解剖、通过率分布、轨迹差异、双轨迹时间线）作为报告视图保留，数据全部来自 Verdict 与 trace。
4. **CI 集成**：Verdict 输出为机器可读 JSON，可以作为合入门禁。

**不做（明确的非目标）：**
- 不做 agent 框架，不做通用观测平台。trace 可以从 Langfuse 等平台导入。
- 不做自动优化器。优化器是 Harness Lab 的"被测对象"，不是它的功能。轨迹按文件系统组织，方便这类优化器直接读取。
- 前期不做模型权重侧的训练。
- 不以 UI 作为真值源。

**后续商业化方向（验证 MVP 后再决定）：**
- 团队版：私有化部署，提供机制库管理、历史 Verdict 查询、模型升级审计报告；
- 服务：为 To B agent 团队做一次性的"harness 体检"，也就是模型升级前后的机制审计。

## 七、竞争定位

| | 通用观测与评测平台（Braintrust / LangSmith / Langfuse） | 自动 harness 优化（Meta-Harness 等） | Harness Lab |
|---|---|---|---|
| 分析单位 | trace、prompt、数据集行 | 整个 harness 代码 | **机制**（带触发点的可开关单元） |
| 核心问题 | 发生了什么；v2 比 v1 分数高吗 | 怎么找到更好的 harness | **改动是否真实有效、归功于谁、哪些该删** |
| 统计严谨性 | 平均分、逐行 diff | 基准分（常被质疑过拟合） | pass^k、置信区间、留出集、同预算基线 |
| 模型升级 | 重新跑一遍，人工比较 | 重新搜索 | 影子触发率，加上有针对性的分叉验证 |
| 部署 | 以 SaaS 为主（Langfuse 可自托管） | 研究代码 | 本地 / 私有化优先 |

关系是**互补而非替代**：从观测平台导入 trace，把 Verdict 回写给 CI 或优化器。

## 八、路线（替代 README 中的 M1–M4）

原路线是"规范 → 契约 → 实现 → 跨实现"，按领域现在的速度太慢。新路线把实现提前，并与论文实验共用同一套代码。

| 阶段 | 时间（约） | 产出 | 验收标准 |
|---|---|---|---|
| **P0 · 重做旗舰实验** | 第 1–3 周 | 在 τ³-airline 上用 2–3 个国产模型重做原先约 +10pp 的实验：k≥4，dev/holdout 切分，同预算重试基线 | 给出带置信区间的结论，无论结论是正还是负 |
| **P1 · 最小契约 + 机制 SDK** | 第 2–5 周 | Mechanism / Config / Trial / Activation / Verdict 的 schema（基于 OTel）；把现有 16 个机制注册为 reactive / persistent，并支持影子模式 | 同一批 trial 能导出为 OTel trace，并被 Langfuse 读取 |
| **P2 · 分叉估计 + CLI** | 第 4–8 周 | 环境快照与分叉重放、对照分叉、`compare` / `attribute` 两个命令 | 分叉估计与全量 LOO 的结论一致率达到论文方案中的预设目标 |
| **P3 · 升级审计 + 报告** | 第 8–12 周 | `upgrade-audit` 命令、静态 HTML 报告（复用现有视觉规范） | 在至少一次真实的模型换代上给出删除候选，并经过验证 |
| **P4 · 第二个框架适配** | 之后 | 在第二个 agent 框架上复用契约 | 同一 Verdict schema 跨两个实现可比 |

## 九、成功指标

- **研究侧**：论文方案中的 RQ1–RQ3 得到明确结论（正面或负面都算）。
- **产品侧**：
  - 在一个真实 To B 项目上，用 `upgrade-audit` 删除至少一个机制，并且线上指标不退化；
  - 一次 `compare` 的算力成本明显低于同等置信度的全量 LOO。具体倍数由 P2 实测给出，不预设。
- **社区侧**：至少一个外部团队用本契约记录自己的机制。

## 十、已定决策（2026-09-25）

1. **第一个适配框架：DeepSeek Harness（dsh）。** dsh 是 MIT 协议、"一切皆插件"的架构，模型适配、工具注册、会话日志乃至 agent loop 本身都是可替换的插件，适合把机制实现为可开关、可影子运行的插件。它目前处于 developer preview，会有不兼容变更，所以适配层要**锁定具体版本**，并把依赖集中在一层很薄的 adapter 里。具体接入设计见 [dsh 适配设计](dsh-adapter.md)。
2. **机制库开源，但先脱敏。** 公开机制的实现与注册元数据；去掉客户名称、业务规则原文、真实提示词片段、内部工具名和接口地址，以及任何来自真实客户数据的样例。脱敏清单在首次公开前单独评审。
3. **P0–P2 只用公开基准**（τ² / τ³ airline、retail，Terminal-Bench 子集）。自建中文 To B 任务集推迟到 P3 之后再评估。
