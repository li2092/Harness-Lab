## 一、研究对象

本工作台所研究的对象，不是单一的语言模型，也不是某一具体的智能体应用，而是 **agent harness**——把模型、工具、上下文、产物、验证、控制等若干本来独立的部件，通过显式的策略和反馈，组成一个有任务目标的执行系统。

在已有的智能体工程实践中，模型常常被作为整个系统的代名词；事实上模型只是这套系统中的一件部件。模型的优劣不能直接说明整个智能体的优劣，正如发动机的输出不能直接说明一辆车的可靠性。把围绕模型而成的这一层称作 harness，是为了把这件被忽略的工程对象显式地命名出来，并对它进行系统化的研究。

## 二、问题的提出

在已部署的 To B 办公、审核、业务流程类智能体系统中，以下几类现象已被反复观察到：

- 演示阶段顺畅通过的智能体，放入合同审核、业务审批、办公任务上反复运行，输出开始出现不一致；
- 同一份提示词在不同时段、不同前缀缓存命中状态下，输出差别巨大；以一次重复评测的平均通过率作为可靠性证据，往往与用户的实际感受不符；
- 给定文档让智能体查阅，它仍可能凭空补出文档中并不存在的细节，而后宣称任务已完成；
- 修改一处工具调用的写法，并不改变模型本身，整条主线却不再收敛。

这些现象的多数原因，不在提示词上，也不在模型上。把希望寄托在反复迭代提示词上，到一定阶段之后边际收益迅速衰减。真正决定智能体是否稳定的，是模型之外那一层 harness 是否被作为工程系统对待。

## 三、雏形：一次围绕 GLM-5 的工程实证

工作台的方法并非凭空提出。在 2026 年早些时候针对 Sierra Research 发布的 τ³-airline 航空客服评测集的一次调试中，已经尝试以一组围绕模型而成的工程机制——工具范围收窄、调用契约修复、策略前置、产出规则等——组合起来约束 GLM-5 模型在此评测集上的行为。

实测结果是：在同一基础模型、同一基线条件下，引入上述一组工程机制后，通过率较基线提升约十个百分点。这一组机制本身并未修改模型权重，亦不依赖于改动模型自身的推理开关。

这一组机制即是后续 harness 工作台所要泛化的初步形态：它们各自针对一类不同的失效，独立可关闭、独立可度量、独立可与基线对照。这一实证亦表明，把围绕模型的这一层抽出来作为独立的工程对象加以处理，是一条有效的方向，不是文献上的设想。

## 四、工作台的设计宗旨

工作台在初期不优化语言模型的权重。它优化的，是模型之外、围绕模型而成的 **harness 策略**：模型路由与升级、工具调用契约、上下文累积、产物落地、验证规则、安全控制。这一类策略，在实际工程中通常以分散的开关、阈值、提示词片段、临时脚本的形式出现，缺乏统一的表达，也缺乏系统化的评估和调整方法。

工作台的任务，不是为已经存在的某一智能体作描述，而是为构造和优化这一类智能体的工程师，提供一套可循的方法。为此，工作台必须同时支持四件性质。这四件性质是控制论意义上的，不是比喻：

1. **可观测性**——任意一次执行的每一步骤、每一次决策的依据、每一件产物的来源与去向，必须能被记录与追溯。
2. **可控性**——每一件机制必须能够独立开启或关闭；任意两份配置之间的差异，必须能在同一组任务上比较。
3. **稳定性**——同一份配置在重复执行下的偏差必须可度量；通过率、成本、轨迹偏移必须有明确的方差与界限。
4. **闭环反馈**——每一次实验的产物，必须能作为下一次实验的输入，使得调整不是孤立事件，而是有依据的迭代。

这四件性质缺一件，工作台都不能作为 harness 工程化的依据来使用。其中，可观测性是其余三件的前提：没有完整的轨迹与决策证据，控制无对象、稳定无度量、反馈无依据。

## 五、当前形态

下图给出工作台的视觉规范与信息架构。这是一份概念稿与规范，不是已部署运行的截图。

![Harness Lab Workbench](docs/screenshots/Harness-Lab.png)

工作台的主要视图按对应关系组织：

- **顶部状态条**记录本次执行的 harness 版本、所用模型、推理强度、任务规模、配置 A 与配置 B 在同一组任务上的整体通过率。
- **左侧栏**列出本次评估涉及的全部机制。机制按对通过率的实测影响分为三类——正向（建议常开）、负向（建议关闭）、中性（场景相关）。每一件机制都可独立开闭，单独度量贡献。
- **中部上方**给出 harness 的八件构成——任务、智能体、模型配置、策略、工具调用、产物、验证、声明。每一件之下挂载所属机制，构成 harness 的纵向解剖图。
- **中部下方**为通过率分布图。基线配置与若干 leave-one-out 探测（每次仅关闭一件机制）在三十项任务、四个套件上的逐项结果排成一图，机制贡献由此可见。
- **右侧**为轨迹差异面板。同一项任务在配置 A 与配置 B 下的执行轨迹自分叉点起逐步对齐，提示词差异、工具调用差异、验证结果差异同行可比。
- **下部**为双轨迹时间线。两份配置的工具调用、产物、验证、声明按真实时刻排列，可在任意时刻暂停、回放、对照。

工作台的当前形态为 v0，仍处于概念稿与规范阶段：视觉与信息架构已成形，组件契约、数据模式、参考实现尚在整理。本仓库的近期目标是把这一套规范文档化，并不在短期内提供一个可直接安装运行的工具。

## 六、与教程的关系

工作台承担工程实现一侧，相应的方法论由独立项目承担。

- 教程项目：[harness-study](https://github.com/li2092/harness-study) · 智能体的工程实践
- 工作台项目（本仓库）：基于这套方法论的可视化工作台规范

两者的分工是：教程定义研究的对象与方法，工作台把这一套方法在可执行的实例上加以承担。教程的读者既包括人，也包括将要替非技术使用者落地智能体的另一个智能体。工作台的使用者既包括手工调整 harness 的工程师，也包括以工作台为输出格式的自动调优过程。

## 七、近期路线

工作台的开发分四步，每一步必须以前一步的稳定为前提。

- **M1 · 规范文档化**：把截图中每一区域、每一条信息、每一个交互对应到一份规范条目，包含含义、数据来源、状态空间。
- **M2 · 数据契约**：定义机制、配置、任务、套件、轨迹、产物的数据模式。任意一次执行均须按此模式记录，以便不同实现之间互相对照。
- **M3 · 参考实现**：在已有的智能体执行环境上接入一个最小可跑的参考实现，验证规范的可行性。
- **M4 · 跨实现对照**：在不同的智能体框架之间复用同一份规范，使工作台不绑定于某一具体实现。

## 八、边界与不做什么

工作台的边界亦须明示。

- **前期不做语言模型权重一侧的训练**；这一侧的优化保留在后续规划中。
- 在 v0 阶段不做完全自动的 harness 演化；任何机制的引入与变更，必须经过显式可比较的对照实验。
- 不以工作台 UI 作为单一真值源；执行日志、轨迹、产物记录仍是真值源，工作台只负责呈现。
- 不复制任何受限源码；对外部的同类项目（如各家公开的智能体编排框架），仅通过公开的接口、命令行、记录、对照实验来对齐。

## 九、谁可参考

- 正在构造或优化某一具体 agent harness 的工程师与研究者；
- 需要评估外部智能体厂商、并对其内部组成形成判断的产品决策者；
- 在搭建评测、调优、回放、可观测性工具的过程中，希望复用一套通用规范的工程团队。
